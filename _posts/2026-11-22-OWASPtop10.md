# OWASP Top 10:2025 A07 — 인증 실패

## 1. 한눈에 보기

**A07:2025 인증 실패(Authentication Failures)**는 애플리케이션이 사용자의 신원을 제대로 확인하지 못해, 공격자를 정상 사용자로 받아들이는 문제이다. 쉽게 말하면 **“로그인한 사람이 정말 계정 주인인지 확인하는 과정에 허점이 있는 상태”**이다.

인증은 **“누구인가?”**를 확인하는 과정이고, 인가는 **“무엇을 할 수 있는가?”**를 정하는 과정인데 예를 들어 다른 사람의 비밀번호로 로그인하는 문제는 인증 실패에 해당합니다. 로그인은 정상적으로 했지만 다른 사람의 자료까지 볼 수 있는 문제는 주로 접근 통제(A01)와 관련된다.

2025년판에서 이 항목은 **7위**를 유지했고, 이름이 2021년의 “Identification and Authentication Failures”에서 “Authentication Failures”로 바뀌었고, OWASP는 이 범주에 36개의 CWE를 연결합니다. OWASP Top 10은 주요 보안 위험을 알리기 위한 자료이므로, 7위라는 숫자를 개별 서비스의 위험도 점수로 해석하면 안된다. 

개인적으로 인증과 인가를 헷갈릴 때가 종종 있었는데, 이번 기회에 “로그인 자체가 뚫렸느냐(A07), 로그인한 뒤 권한 선을 넘었느냐(A01)”로 기준을 잡고 보니 훨씬 명확해졌다.

## 2. 어떤 문제가 포함되나?

A07은 비밀번호 입력 화면만의 문제가 아니다. 계정 생성부터 로그인, 인증 수단 복구, 세션 유지와 로그아웃까지 **사용자의 신원을 확인하고 그 상태를 안전하게 유지하는 전체 과정**을 다룬다.

| 문제 유형 | 쉬운 설명과 예 |
|---|---|
| **유출된 비밀번호 재사용** | 다른 사이트에서 유출된 아이디와 비밀번호 조합을 여러 사이트에 자동으로 넣어 보는 공격. |
| **무차별 대입·비밀번호 추측** | 로그인 시도를 빠르게 반복하는데도 서비스가 적절히 제한하지 않는 경우. |
| **약한 기본 비밀번호** | 관리자 계정이 `admin/admin` 같은 초기 비밀번호를 그대로 사용하는 경우. |
| **취약한 계정 복구** | “어머니의 성함은?” 같은 쉽게 알아내거나 추측할 수 있는 답만으로 계정을 되찾게 하는 경우. |
| **안전하지 않은 비밀번호 저장** | 비밀번호를 평문이나 빠르게 계산되는 해시로 저장해, 데이터베이스가 유출됐을 때 쉽게 알아낼 수 있는 경우. |
| **MFA[^1] 우회 또는 부실한 대체 수단** | 다중 인증을 제공하지 않거나, 인증 앱을 잃어버렸을 때 너무 약한 절차로 바로 로그인하게 해 주는 경우. |
| **세션 관리 오류** | 로그인 전후에 같은 세션 ID를 쓰거나, 로그아웃 후에도 서버가 세션을 유효하게 받아들이는 경우. |

OWASP가 제시하는 대표 사례에는 유출된 비밀번호를 응용해 `Winter2025`를 `Winter2026`으로 바꿔 시도하는 공격도 있습니다. 따라서 단순히 똑같은 비밀번호만 대조하는 방어로는 부족할 수 있다.
## 3. 공격은 어떻게 이어지나?

쇼핑몰이 로그인을 여러 번 시도해도 별다른 제한을 두지 않고, 흔히 유출된 비밀번호도 허용한다고 생각해보면

1. 공격자가 다른 서비스에서 유출된 로그인 정보를 확보.
2. 자동화 도구로 해당 쇼핑몰의 로그인 화면에 여러 조합을 입력.
3. 계정 하나에 들어가면 저장된 주소, 주문 내역, 결제 관련 정보에 접근하거나 피해자 계정으로 물건을 주문.
4. 로그아웃 후에도 세션이 살아 있거나, 계정 복구 절차가 약하면 공격자가 접근을 계속 유지.

이 사례는 **비밀번호 정책, 로그인 시도 제한, 추가 인증, 세션 종료**가 서로 연결되어야 하는 이유를 보여준다. 어느 한 단계에 큰 허점이 있으면 다른 방어 조치도 무력화될 수 있습니다. 

## 4. 어떻게 예방하나?

### 비밀번호를 추측하기 어렵게 관리하기

- `admin`, `Password1`처럼 흔하거나 알려진 비밀번호와 유출된 비밀번호를 새 비밀번호로 설정하지 못하게 한다.
- 사용자가 비밀번호 관리자를 이용할 수 있도록 지원한.
- 비밀번호를 평문으로 저장하지 않습니다. OWASP는 비밀번호에 고유한 salt[^2]를 적용하고 Argon2id[^3], bcrypt[^4], PBKDF2[^5] 같은 **비밀번호용 적응형 해시**를 사용하도록 안내함. 빠른 일반 해시인 SHA-256[^6]만으로 비밀번호를 저장하는 것은 적절하지 않다. 
- 비밀번호를 정기적으로 바꾸게 하기보다, 유출이 의심될 때 변경하게 하고 흔하거나 유출된 비밀번호를 사용하지않는다. 
### 로그인과 복구 시도를 제한하기

- 로그인 실패가 반복되면 시도 횟수를 제한하거나 점차 지연시켜 자동화 공격을 어렵게 함.
- 특정 계정을 너무 쉽게 잠그면 공격자가 다른 사람의 로그인을 방해할 수 있으므로 제한 방식을 신중히 설계한다.
- 계정이 존재하는지 추측하지 못하도록, 존재하지 않는 계정과 비밀번호가 틀린 계정에 비슷한 메시지를 보여 준다.
- 비밀번호 재설정 링크나 코드는 충분히 무작위로 만들고, 한 번만 사용할 수 있게 하며, 일정 시간이 지나면 만료시킨다. 

### MFA[^1]를 켜고, 복구 경로도 보호하기

MFA[^1]는 비밀번호 외에 별도의 인증 요소를 추가한다. 예를 들어 **비밀번호(알고 있는 것) + 보안 키(가지고 있는 것)**이 해당한다. 비밀번호와 PIN처럼 같은 종류의 요소를 두 번 묻는 것은 서로 다른 요소를 쓰는 MFA[^1]가 아니다

여러 단계 인증을 켜도 비밀번호 찾기나 계정 복구, 앱·프로그램을 통한 로그인 절차가 허술하면 공격자가 그 경로로 계정에 들어올 수 있다. 따라서 평소 로그인뿐 아니라 이런 절차도 함께 확인해야 한다.

### 로그인 후 세션도 안전하게 다루기

로그인에 성공하면 서버는 로그인 상태를 기억할 새 번호(세션 ID)를 발급합니다. 이 번호는 다른 사람이 쉽게 알아맞힐 수 없어야 하고, 웹 주소(URL)에 넣지 않아야 한다. 로그인 상태를 기억하는 쿠키에는 `Secure`[^7]와 `HttpOnly`[^8] 설정을 적용한다. 로그아웃하거나 한동안 사용하지 않거나 정해 둔 최대 시간이 지나면, 서버가 이 번호를 더 이상 받아들이지 않도록 해야 한다. 그래야 누군가 예전 번호를 알아내더라도 계속 로그인하지 못한다. 

## 5. 핵심 정리

마지막으로 정리를 하자면 A07을 이해할 때는 다음 세 가지를 기억하면 .

1. **인증은 로그인 한 번으로 끝나지 않는다.** 계정 복구, MFA, API 로그인, 세션 종료도 모두 인증 안전성의 일부이다.
2. **한 가지 방어만으로는 부족함.** 강한 비밀번호, 시도 제한, MFA, 안전한 세션 관리를 함께 적용해야 한다.
3. **잘못된 복구·대체 절차가 로그인 우회로가 될 수 있다.** 평소 로그인만큼 계정 복구와 MFA 변경 절차도 엄격하게 보호해야함.

[^1]: **MFA(다중 인증)**는 서로 다른 인증 요소를 두 가지 이상 조합해 사용자의 신원을 확인하는 방식이다.

    - **지식 요소:** 비밀번호, PIN 번호
    - **소유 요소:** OTP 앱, 보안 키
    - **생체 요소:** 지문, 얼굴 인식

[^2]: **Salt**는 비밀번호 등을 해시 처리하기 전에 원본 데이터에 덧붙이는 임의의 난수 문자열임.

[^3]: **Argon2id**는 비밀번호를 안전하게 보관할 때 쓰는 계산 방식이다. 비밀번호를 다른 값으로 바꿔 저장하고, 그 값이 유출돼도 여러 비밀번호를 빠르게 대입하기 어렵도록 계산에 시간과 메모리가 들게 한다.

[^4]: **bcrypt**는 비밀번호를 저장할 때 쓰는 계산 방식이다. 계산량을 조절할 수 있어, 저장된 값이 유출돼도 비밀번호를 여러 개 대입해 맞히는 데 더 많은 시간이 든다.

[^5]: **PBKDF2**는 비밀번호와 임의의 값(salt)을 넣어 계산을 여러 번 반복하고, 그 결과를 저장용 값으로 만드는 방식이다. 반복 횟수가 많을수록 비밀번호를 추측하는 데 더 많은 계산이 필요하다.

[^6]: **SHA-256**은 데이터를 256비트 길이의 결과값으로 바꾸는 빠른 계산 방식(해시 함수)이다. 비밀번호 저장에 단독으로 사용하면 공격자가 비밀번호 후보를 빠르게 많이 시험할 수 있어 적절하지 않다.

[^7]: **`Secure`** 설정은 쿠키가 암호화된 HTTPS 연결에서만 전송되도록 한다.

[^8]: **`HttpOnly`** 설정은 웹페이지의 JavaScript가 쿠키 내용을 직접 읽지 못하게 한다.
